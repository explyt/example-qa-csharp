# О тестируемом приложении

## 1) Аутентификация
- Тип: JWT-токен (Bearer Authentication)
- Аутентификация происходит через микросервис AuthService
- Логин-эндпоинт: POST /api/User
- Тело запроса: JSON объект с полями Login и Password
- После успешной аутентификации сервер возвращает JWT токен, который должен использоваться в заголовке Authorization: Bearer {token} для всех последующих запросов

Пример запроса:
```
POST /api/User
Content-Type: application/json

{
  "Login": "admin",
  "Password": "admin"
}
```

Пример ответа:
```json
{
  "Token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "UserName": "admin",
  "Roles": ["SALESMAN", "USER"],
  "Avatar": "static/avatars/admin.png",
  "UserType": "SALESMAN",
  "ExpiryTimeStamp": "2023-12-31T23:59:59Z"
}
```

## 2) Формат ошибок
- При неверных учетных данных возвращается 400 Bad Request с телом:
```json
{
  "message": "Username of password incorrect"
}
```

## 3) Тестовые данные
- Доступные тестовые пользователи (логин/пароль):
  - jimmy.solid / secret
  - danny.solid / secret
  - admin / admin
- Все пользователи имеют одинаковые роли: ["SALESMAN", "USER"]
- Аватары хранятся в статических файлах

## 4) Уникальность пользователей
- Уникальность проверяется по полю Login
- В текущей реализации пользователи хранятся в in-memory базе данных (InsuranceAgentsInMemoryDb)
- Невозможно зарегистрировать двух пользователей с одинаковым логином

## 5) Верификация аутентификации
- Для проверки валидности токена можно использовать любой защищенный эндпоинт
- Например, GET /api/User - возвращает информацию о текущем пользователе

## 6) Требования к паролю
- В текущей реализации нет специальных требований к сложности пароля
- Пароли хранятся в открытом виде в in-memory базе данных
- При реализации полноценного функционала рекомендуется использовать хэширование паролей (например, bcrypt)

## 7) Требования к окружению/очистке
- Пользователи определяются при запуске приложения и хранятся в памяти
- После перезапуска сервиса все изменения сбрасываются
- Добавление/удаление пользователей в runtime не предусмотрено в текущей реализации

## 8) Полезные эндпоинты для тестов
- Аутентификация:
  - POST /api/User (логин/пароль в теле запроса)
- Получение информации о пользователе:
  - GET /api/User (требуется действующий JWT токен)

## 9) Замечания по безопасности и заголовкам
- Все защищенные эндпоинты требуют заголовок Authorization: Bearer {token}
- JWT токены имеют срок действия (7 дней по умолчанию)
